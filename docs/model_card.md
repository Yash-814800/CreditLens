# Model card: CreditLens scorecard (`scorecard_v1` / `policy_v1`)

Following the spirit of Model Cards for Model Reporting (Mitchell et al., 2019), adapted for a
transparent additive scorecard rather than a trained black-box model — most of the sections below
describe a *policy configuration*, not learned weights, which is itself the central design choice
this card explains.

## Intended use

Decision support for underwriters evaluating unsecured, small-ticket credit line applications from
**new-to-credit (NTC) / thin-file gig workers in India**, using alternative data (gig-platform
payout history, utility bill payment history, bank/UPI cash-flow) in place of, or alongside, a
traditional credit bureau record. Output is one of three tiers (APPROVE / REFER for manual review /
DECLINE), a fully itemised score breakdown, up to four principal reason codes, a counterfactual
recourse path, and a plain-English grounded summary — always with a human underwriter able to
override the system outcome (`POST /api/v1/applications/{id}/override`, mandatory reason, both the
system and final outcome are retained and audited).

## Out-of-scope use

- **Not a fully automated decisioning system.** Every application produces a system recommendation;
  `REFER` and any override path exist specifically because this is designed for human review, not
  autonomous approval/decline at scale without oversight.
- **Not validated on real applicants or real repayment outcomes.** Every number in this repo's
  reports (`docs/validation_report.md`, `docs/fairness_report.md`, `docs/fraud_eval.md`) is computed
  against **synthetic data** (see `docs/data_card.md`). Nothing here demonstrates real-world
  predictive accuracy, and this system must not be deployed against real applicants without a real
  validation study, real regulatory review, and real consent/data-sourcing infrastructure.
- **Not a general-purpose credit model.** The 7 scorecard factors, the document types, and the
  reason codes are specific to this exact use case (gig-worker alternative data); the design does
  not generalise to, say, mortgage or auto-loan underwriting without a full re-derivation of the
  scorecard and policy from scratch.
- **Not for use as the sole basis of an adverse action without human review of the underlying
  factors** — the adverse-action notice (`app/services/explain/adverse_action.py`) is structured to
  support human-reviewable, appealable communication, not to be sent unread.

## Data provenance

100% synthetic, generated by `datagen/synthgen/` (Phase 2). Three data products:
1. **Fraud-evaluation corpus** (`data/synth/documents/`, gitignored, regenerable via `make datagen`):
   240 clean + tampered documents across the 3 document types, with reuse variants and hard
   negatives, used to tune and evaluate the fraud/integrity layer (`docs/fraud_eval.md`).
2. **Historical borrower dataset** (`data/synth/history.parquet`, 2,000 rows): generated from a
   latent creditworthiness variable plus an *unobserved* shock, so `defaulted` is never derived from
   the same features the scorecard scores — avoiding circular validation. Full generative design and
   real summary statistics in `docs/data_card.md`.
3. **Demo personas** (`data/demo_pack/`, committed, 11 hand-crafted profiles P01–P11) with documented
   target signals, used for the deterministic pipeline demo and automated integration testing
   (including P09 adversarial prompt injection, P10 blind-spot cohort downgrade, and P11 resilient
   cohort upgrade; see `docs/PROGRESS.md`'s persona sweep tables).

No real applicant data, real document images, or real bureau data was used anywhere in this system's
construction, tuning, or evaluation.

## Factors and weights (versioned: `scorecard_v1.yaml`, policy: `policy_v1.yaml`)

Additive scorecard: `score = clamp(base + sum(factor points), 0, 100)`, `base = 15`.

| Factor | Direction | Max up | Max down | Reason code on penalty |
|---|---|---|---|---|
| `utility_tenure_months` | higher is better | +25 | -10 | RC01 |
| `weekly_inflow_cv` | lower is better | +15 | -30 | RC03 |
| `utility_on_time_ratio` | higher is better | +15 | -15 | RC02 |
| `avg_daily_balance_inr` | higher is better | +10 | -10 | RC04 |
| `gig_active_days_per_week` | higher is better | +8 | -8 | RC05 |
| `income_reconciliation_ratio` | higher is better | +7 | -10 | RC06 |
| `authenticity_score` | higher is better | +5 | -25 | RC07 |

Positive maxima sum to 85 (+ base 15 = 100 for a perfect profile). A missing factor (its source
document was never submitted) contributes exactly 0 points — treated as *unknown*, never as a
penalty — and instead lowers `data_completeness`, which independently caps the outcome at REFER
below a configured threshold (never DECLINE for thin data alone; see `policy_v1.yaml`'s completeness
gate and CLAUDE.md's non-negotiable rule 7). Full bin edges, labels, and the calibration rationale
(including a documented, deliberate deviation from naive quantile-anchored bins — see
`scorecard_v1.yaml`'s own header comment and `docs/PROGRESS.md`'s Phase 5 section) live in the
YAML file itself, which is the actual source of truth, not this card.

**Policy rule order** (`decision.py::decide`, every evaluation traced into an explicit
`rules_fired` audit list): (1) fraud severity HIGH → hard DECLINE; (2) fraud MEDIUM / identity
mismatch / suspected prompt-injection → capped at REFER; (3) incomplete data or low extraction
confidence → capped at REFER, never DECLINE; (4) score tiers (APPROVE ≥ 70, REFER 45–69, DECLINE
< 45, all configurable); (5) the two-signal precedent rule (a real pgvector k-NN peer comparison
using 10 continuous embedding dimensions that can downgrade an APPROVE to REFER if the 95% Wilson CI
lower bound on peer default rate exceeds `max_acceptable_default_rate_for_approve=0.15`, or upgrade a
DECLINE to REFER if peer default rate CI upper bound is below `min_acceptable_default_rate_for_decline=0.19`,
preserving hard HIGH fraud declines; see `docs/two_signal_eval.md`); (6) credit-limit sizing capped
by verified income and an absolute ceiling.

## Fairness safeguards

- **Allowlist sanitizer, not a denylist** (`app/services/guardrails/sanitizer.py`, CLAUDE.md rule
  7): only the 7 scorecard factors (+ 4 supporting features used elsewhere in the pipeline) ever
  reach the scorer. Name, phone, PAN/Aadhaar, address/pincode, gender, age, religion, caste, marital
  status, and free-text vocation are structurally incapable of influencing the score — not filtered
  out by a rule that has to *recognise* them, but excluded by construction because they were never
  on the allowlist in the first place. This also means an unanticipated proxy feature is caught the
  same way a named protected attribute is — proven as an executable regression test
  (`backend/tests/unit/test_fairness_proxy_rejection.py`) and verified across 200 Hypothesis profiles
  in property tests (`backend/tests/unit/test_scoring_properties.py`), proving zero change to `ScoringInput`,
  score, or `Decision` outcome.
- **Fairness audit harness** (`scripts/fairness_audit.py` → `docs/fairness_report.md`):
  Evaluated on the held-out `data/synth/history.parquet` **TEST split** ($n=418$):
  - **Overall four-fifths rule:** Group A approval is 37.1% (85/229), Group B approval is 32.8% (62/189),
    yielding an Adverse-Impact Ratio (AIR) of **0.884** (threshold $\ge 0.80 \rightarrow$ **PASS**).
  - **Cohort breakdown & invariants:** Monitored across all cohorts. The `blind_spot` cohort reaches 100.0%
    scorecard approval for both groups (AIR = 1.000) due to pristine utility histories, while the `resilient`
    cohort has 0.0% scorecard approval for both groups (AIR = 1.000) due to thin utility histories. Small
    cohorts (e.g., `rural_mixed` at $n=41$) exhibit sample-induced AIR fluctuations, emphasizing the need
    for confidence intervals.
  - **Access-to-credit mechanism vs. bureau-only strawman:** Against a traditional bureau-only policy that declines
    100% of thin-file NTC applicants (0% approved, 0% referred), CreditLens alternative data yields +35.2% outright
    approvals and +18.4% referrals for manual underwriter review (net 53.6% expanded access).
- **Adversarial proxy feature experiment:** When a synthetic demographic proxy (`pincode_zone_risk`) is injected,
  an unprincipled strawman model's AIR plunges to **0.236** (**FAIL**), proving the audit harness reliably catches
  disparate impact. In contrast, CreditLens's fail-closed allowlist sanitizer unconditionally drops the proxy feature,
  maintaining identical clean-baseline scoring (AIR = **0.884**, **PASS**).
- **Limitations & production compliance requirements**:
  - *Synthetic labels:* `group_label` is synthetic and independent of features by construction ($\max |r| \le 0.041$),
    so a pass is expected and validates the harness rather than proving real-world fairness.
  - *Small samples & intersectionality:* Sub-cohort variance requires larger samples; real audits must measure multi-axis intersectionality (gender $\times$ geography $\times$ age).
  - *Production requirements:* A live lending deployment requires real demographic outcome monitoring, quarterly
    adverse-impact reviews, and systematic Less-Discriminatory-Alternative (LDA) searches across feature weights
    and data sources to minimize disparate impact.

## Explainability features

- **Full factor breakdown**: every point gained or lost, with a human-readable bin label, exposed
  via `GET /api/v1/meta/scorecard` and rendered as a waterfall chart in the underwriter cockpit.
- **Up to 4 principal reason codes**, ordered by points-shortfall vs. each factor's best bin
  (FCRA/ECOA "key factors" convention), each mapped to plain-language text.
- **Counterfactual recourse** (`app/services/scoring/recourse.py`): concrete, actionable,
  time-bound next steps, each one verified by literally re-scoring the counterfactual profile before
  it is ever shown to an applicant — never a plausible-sounding but unverified suggestion.
- **Grounded LLM summary** (`app/services/explain/summary.py` + `grounding.py`): a plain-English
  narration of the decision whose every number is checked against the computed values that actually
  produced it; an ungrounded attempt is rejected and replaced by a deterministic, grounded-by-
  construction template — with the UI always showing which path was actually used
  (`source: llm | template`, `verified: bool`).
- **Adverse-action notice**: structured, FCRA/ECOA-shaped JSON with an explicit note that a real
  India deployment would map its wording to RBI digital-lending / fair-practice expectations rather
  than claiming US-regulation compliance it does not have.

## Human-in-the-loop

Every decision can be overridden by an authenticated `underwriter`, with a **mandatory** reason,
before it becomes final. The system's original outcome and the human's final outcome are both
retained (`applications.outcome` vs. `applications.final_outcome`) and the override itself is a
first-class, hash-chain-audited event (`DECISION_OVERRIDDEN`). This is a deliberate design choice,
not a fallback: CLAUDE.md rule 3 and this card's "Out-of-scope use" section both treat full
automation as explicitly outside this system's intended use.

## Known limitations

- Synthetic data throughout — see "Data provenance" above and every report's own limitations
  section (`docs/fraud_eval.md`, `docs/validation_report.md`, `docs/fairness_report.md`,
  `docs/extraction_eval.md`, `docs/two_signal_eval.md`, `docs/injection_eval.md`).
- **Planted two-signal cohorts caveat:** The blind-spot (6.5%) and resilient (7.4%) cohorts in the
  synthetic history dataset were explicitly designed and planted to stress-test and prove the two-signal
  precedent override mechanism. While the 68.8% blind-spot catch rate and 82.8% resilient recovery rate
  demonstrate the mathematical mechanics of precedent Wilson CI intervals (`docs/two_signal_eval.md`),
  they reflect designed stress scenarios rather than naturally occurring cohort prevalence.
- **Prompt-injection residual risk:** The multi-layer defense successfully detected and neutralized
  6/6 test attacks across visible, low-contrast, and in-field vectors (`docs/injection_eval.md`).
  However, residual risk remains for adversarial text rendered at micro-resolutions below the vision model's
  perceptual threshold or complex steganographic payloads that evade OCR attention.
- The fraud/integrity layer has measured, honestly-reported blind spots: internally
  arithmetic-consistent full-document edits (`consistent_edit`) and geometric transforms that defeat
  perceptual hashing (crop/rotate) — see `docs/fraud_eval.md`.
- `GEMINI_VISION_MODEL`'s extraction has one documented weak field (`GIG_PAYOUT.platform_name`,
  ~30% exact-match accuracy on a naming-convention edge case — see `docs/extraction_eval.md`); every
  other field is ≥82%, most 100%.
- Single-node deployment (`FastAPI BackgroundTasks`, not a durable queue) — a killed container
  mid-pipeline-run loses the in-flight task, though never leaves a partial decision on disk (see
  `docs/threat_model.md`'s STRIDE table, row 6).
- No real bureau data integration exists or is claimed.

## Monitoring plan (for a real deployment; not implemented in this hackathon build)

- **Population Stability Index (PSI)** on the incoming feature distributions vs. the calibration
  population, to detect drift in the applicant mix.
- **Periodic adverse-impact re-testing** (the same four-fifths methodology `fairness_audit.py`
  implements here) against real, lawfully-collected group data on a fixed cadence — directly
  modelled on Upstart's CFPB no-action-letter commitment.
- **Default-rate-by-score-band recalibration**: re-running `scripts/validate_scorecard.py`-style
  analysis against real observed repayment outcomes once they exist, to check the scorecard's
  discrimination (AUC/Gini/KS) and calibration haven't drifted.
- **Recourse-gaming monitoring**: tracking whether applicants' coachable features (e.g. average
  daily balance) show suspicious step-function jumps right before reapplication — the specific
  countermeasure `docs/recourse_gaming_risk.md` calls for.

## Versioning and change control

Every config that drives a decision is an explicit, versioned file, never an inline constant:
`scorecard_v1.yaml`, `policy_v1.yaml`, `fraud_policy_v1.yaml`, `embedding_v1.yaml`,
`calibration_v1.json`, `consent_v1.md`. A future retuning ships as `_v2` files, not an in-place edit — every
`applications` row already records `scorecard_version`/`policy_version` at decision time (see
`app/db/models.py`), so a historical decision remains explainable against the exact config version
that produced it even after the live config moves on.

## Consent, privacy, and data lifecycle

- **Server-side consent gating:** Every submission requires affirmative consent with active version matching (`consent_v1.md`, served via public `GET /api/v1/meta/consent` with SHA-256 integrity hash). Submissions with missing consent or stale versions are rejected server-side with HTTP 422.
- **Zero-PII audit trail:** The `APPLICATION_SUBMITTED` audit row records `consent_at`, `consent_text_version`, and `consent_text_sha256` with zero applicant PII in the payload.
- **Right to withdraw & retention purge:**
  - Applicants can withdraw consent at any time (`POST /api/v1/applications/{id}/withdraw-consent`), marking `consent_withdrawn_at` and recording a `CONSENT_WITHDRAWN` audit entry.
  - An admin-only purge endpoint (`POST /api/v1/admin/retention/purge`, configurable `RETENTION_DAYS=90`, supporting `dry_run: bool = True`) permanently deletes document files/overlays, redacts applicant PII and extracted fields, and records `RETENTION_PURGE` in the audit log.
  - Anonymized decision records and the tamper-evident cryptographic hash chain remain 100% valid after purge (`verify_chain` invariant).

## Why no agent framework and no black-box model

CLAUDE.md rule 3 (no black-box decisioning) and rule 6 (pure functions, no I/O in scoring/policy
logic) are direct answers to what a hiring panel — or a regulator — asks first about an automated
credit decision: *why did this specific applicant get this specific outcome, and can you prove it?*
An agent framework (an LLM choosing which tools to call, in what order, with what reasoning) adds a
non-deterministic, non-reproducible decision path exactly where auditability matters most; a trained
black-box model (even a well-performing one) cannot produce the itemised, regenerable-by-hand factor
breakdown this system's explainability and adverse-action requirements depend on. The two places an
LLM *is* used — document field extraction into a strict schema, and a plain-English summary grounded
strictly in already-computed values — are both chosen because they are the only two places CLAUDE.md
rule 3 permits an LLM to participate at all: neither one ever scores, decides, or overrides anything
a human or a regulator would need to independently re-derive from the versioned scorecard and policy
files alone.
