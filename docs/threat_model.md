# Threat model

Phase 7 seeded this file with one frontend-specific trade-off (below). This
Phase 8 pass adds the full STRIDE-lite table plus the results of the actual
security scans run against this repo.

## STRIDE-lite table

| # | Asset | Threat (STRIDE category) | Mitigation actually implemented | Residual risk |
|---|---|---|---|---|
| 1 | Applicant PII (name, phone, PAN, Aadhaar, address) | **Information disclosure** via logs, API responses, or the DB | Allowlist sanitizer (`app/services/guardrails/sanitizer.py`) strips PII before it ever reaches the scorer; Aadhaar is never stored (HMAC-SHA256 + pepper only, `core/security.py`); PAN/phone are masked on every API response (`schemas/applications.py`); structlog's PII-redaction processor (`core/logging.py`) redacts known key names AND regex-matches PAN/Aadhaar/phone-shaped values anywhere in a log line, even inside free text | A field renamed to something the redaction regexes don't recognise could leak in a future log line — mitigated by the allowlist being independent of the log redaction (defense in depth, not a single point of failure) |
| 2 | JWT auth tokens | **Spoofing** / session hijack via XSS-exfiltrated token | sessionStorage (not localStorage) — see the dedicated section below; no `dangerouslySetInnerHTML` anywhere; Jinja2 `tojson` escaping on the adverse-action notice; React's default JSX escaping | A token is still readable by any script running *while the tab is open* — sessionStorage narrows the persistence window, it does not eliminate in-session XSS risk. Production next step: HttpOnly/Secure/SameSite cookie + CSRF token (documented below, not implemented here) |
| 3 | Uploaded documents (images/PDF/CSV) | **Tampering** — a forged or reused document used to obtain credit under false pretences | pHash collision detection with corroboration (`services/fraud/phash.py`), ELA + noise-residual tamper radar, per-doc-type arithmetic/chronology checks, metadata forensics — all empirically tuned via `scripts/eval_fraud.py`, never hand-guessed thresholds | Documented, measured misses: `consistent_edit` (a coherent, internally-consistent full-document edit) and geometric pHash-defeating transforms (crop/rotate) — see `docs/fraud_eval.md`'s own limitations section. This is a real, honestly-reported detection gap, not a false claim of completeness |
| 4 | Uploaded documents as an LLM input channel | **Prompt injection** — document text crafted to manipulate the extraction model into ignoring instructions, exfiltrating other applicants' data, or fabricating favourable fields | The vision prompt (`prompts/*_extraction.v2.md`) explicitly states the image is untrusted data and instructions embedded in it must never be followed; every extracted field is range/format-validated before use (`services/extraction/guardrails.py`); regex pattern scanning flags known jailbreak strings; model-flagged instruction findings trigger confidence reduction. **Empirically verified in `docs/injection_eval.md`** across 6 adversarial documents (visible, low-contrast, in-field): 6/6 were detected, 0 numeric scorecard distortions occurred (delta = 0.0), and 100% were capped at REFER with RC07. The LLM never scores or decides anything (CLAUDE.md rule 3) | A sufficiently subtle injection rendered in micro-text below the vision model's resolution threshold or within legitimate feature bounds could evade prompt-level flags. Cross-document reconciliation (income vs. bank credits) acts as an independent defense |
| 5 | The counterfactual recourse advice shown to applicants | **Model gaming** — an applicant temporarily manipulating a coachable feature (e.g. depositing cash before reapplying to inflate `avg_daily_balance_inr`) to defeat the scorecard without a real change in creditworthiness | `recourse.py` only ever suggests actionable, forward-looking behaviour changes (never a one-time deposit dressed up as "raise your balance"); non-coachable/gameable factors (`weekly_inflow_cv`, `authenticity_score`) are permanently excluded from recourse suggestions; see `docs/recourse_gaming_risk.md` for the full scenario-by-scenario writeup | A determined applicant can still game `avg_daily_balance_inr` short-term; the documented production countermeasure is balance-history monitoring over the full window a real deployment would see (not just the applicant-supplied bank CSV snapshot this hackathon build accepts) — noted as a real, unclosed gap, not solved here |
| 6 | The underwriting decision pipeline | **Denial of service / repudiation** — a crashed pipeline run silently leaving a half-written or ambiguous decision, or a decision no one can later prove was actually made this way | `pipeline.py` catches any exception into `stage=FAILED` + a stable `error_code`, never a partial `DecisionArtifact`; idempotent re-runs (each stage deletes-then-reinserts its own rows); every stage writes a hash-chained audit event (`services/audit/service.py`) — `GET /audit/verify` proves the chain hasn't been altered after the fact, and the immutability trigger blocks UPDATE/DELETE/TRUNCATE on `audit_log` for every role including the DB admin/superuser | `BackgroundTasks` (FastAPI's in-process executor) means a killed *container* mid-run (not just a killed request) loses the in-flight task with no automatic retry/resume — a real deployment needs a durable queue/worker (SQS, documented in `docs/deployment.md`); a `FAILED` stage is still recoverable/re-triggerable by resubmission, so this is a durability gap, not a silent-corruption one |
| 7 | The historical-borrower dataset / scorecard weights | **Fairness / adverse-impact** risk from alternative-data features silently correlating with a protected attribute (redlining-by-proxy) | Allowlist sanitizer means protected attributes structurally cannot reach the scorer at all — not a fairness *mitigation* on a black-box model, but a stronger guarantee (they are never inputs); `docs/data_card.md` reports the synthetic history's own measured max feature-vs-`group_label` correlation (0.041); `scripts/fairness_audit.py` confirms AIR=0.884 (PASS) and proves that an adversarial proxy feature drops AIR to 0.236 (FAIL) but is 100% neutralized by the fail-closed sanitizer | The synthetic history's blind-spot (6.5%) and resilient (7.4%) stress cohorts are planted to prove the mechanism (`docs/two_signal_eval.md`), and `group_label` is synthetic. In real-world data, socioeconomic factors correlate with demographics, requiring continuous post-issuance monitoring as detailed in `docs/fairness_report.md` |
| 8 | Postgres role/credential boundary | **Elevation of privilege** — the running app gaining the ability to rewrite its own audit trail | `APP_DB_USER` (the role the live app connects as) has only SELECT/INSERT on `audit_log`, enforced by both an explicit `REVOKE` and a `BEFORE UPDATE/DELETE/TRUNCATE` trigger that `RAISE EXCEPTION`s for *every* role including `POSTGRES_USER`/superuser; migrations always run as the separate admin role, never the app's own `DATABASE_URL` | A superuser with direct psql access and sufficient intent could still `ALTER`/drop the trigger itself (Postgres has no true immutable-table primitive) — documented here rather than overclaimed; the real guarantee is against the *application's own* code path, plus tamper-evidence (the hash chain would visibly break) if the trigger were ever bypassed out-of-band |
| 9 | Secrets (DB passwords, `JWT_SECRET`, `HMAC_PEPPER`, `GEMINI_API_KEY`) | **Information disclosure** via commit history, logs, or CI | `.env` is gitignored and confirmed never committed (see security-scan results below); `production_guard_errors()` refuses to boot if any secret is missing, short, or left at its `.env.example` placeholder; CI never has real secrets in its config (see `.github/workflows/ci.yml`); AWS deployment (Phase 9) moves secrets to SSM Parameter Store, never Terraform state | A developer manually pasting a secret into a chat/PR description is a process risk no code control fully closes — mitigated procedurally (CLAUDE.md rule 2 tells the agent never to print/echo secrets) rather than technically |
| 10 | Applicant consent / terms integrity | **Repudiation / Tampering** — submitting applications without valid consent or with altered/stale terms | Server-side consent enforcement (`api/v1/applications.py`, `api/v1/demo.py`) rejects submissions with HTTP 422 unless `consent_accepted: true` AND `consent_text_version` strictly matches the active version (`consent_v1.md`); SHA-256 hash verified; immutable `APPLICATION_SUBMITTED` audit log records `consent_at`, `consent_text_version`, and `consent_text_sha256` with zero PII | Client-side checkbox tampering is impossible since server validates version and state. A production deployment would augment this with OTP verification or digital signatures for non-repudiation against the human applicant |
| 11 | Retained documents & applicant PII | **Information disclosure / Right-to-erasure violation** — holding sensitive document images and KYC PII indefinitely | Configurable retention period (`RETENTION_DAYS=90`); consent withdrawal endpoint (`POST /api/v1/applications/{id}/withdraw-consent`) logs `CONSENT_WITHDRAWN`; admin purge (`POST /api/v1/admin/retention/purge`, supporting `dry_run: bool = True`) permanently deletes storage files/overlays, redacts applicant PII (`name = "[REDACTED]"`, hashes cleared) and extracted fields, and logs `RETENTION_PURGE` while preserving anonymized decisions and verifying the cryptographic hash chain | Backups created prior to a purge retain data until backup lifecycle expiration; mitigated by setting backup rotation policies to align with `RETENTION_DAYS` |

## Security-scan results (run against this exact repo state; commands are re-runnable)

- **`pip-audit`** (backend dependencies): **0 known vulnerabilities.** (`creditlens-backend` itself is skipped as a local, unpublished package — expected, not a gap.)
- **`npm audit`** (frontend dependencies, prod + dev): **0 vulnerabilities.**
- **`bandit -r app`** (backend source): 8 low-severity findings, all reviewed and accepted, none fixed with a `# nosec` suppression (kept visible instead of silenced):
  - 6× `B101 assert_used` — every instance is a type-narrowing assertion *after* the condition was already established by preceding logic (e.g. `assert user is not None` right after a successful login check, or `assert isinstance(extraction, GigPayoutExtraction)` right after branching on `doc_type == "GIG_PAYOUT"`), not a security boundary check silently disabled by `python -O`. Accepted as-is.
  - 2× `B105 hardcoded_password_string` — these are the literal *placeholder* strings (`"change-me-to-a-random-32-plus-character-secret"` etc.) that `production_guard_errors()` compares real secrets against to refuse startup if left unchanged. Bandit's pattern-matcher cannot distinguish a placeholder-comparison constant from a real hardcoded credential; there is no actual secret here. Accepted as a false positive.
- **Secrets scan (`gitleaks`)**:
  - `gitleaks git` (full commit history, all 10 commits at time of scan): **no leaks found.**
  - `gitleaks dir` (the full working tree, including gitignored files): found the real local secrets **inside `.env` only** (`POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `JWT_SECRET`, `GEMINI_API_KEY`, the three `DEMO_*_PASSWORD`s) — this is the *expected*, correct state (a real secret must exist locally for the app to run at all); the point of the scan is that none of them appear in git history, which the first scan confirms. `git status` independently confirms `.env` has never been tracked.
- **PII-in-logs**: covered by an existing automated test (`tests/unit/test_logging.py`'s PII-redaction assertions, `capsys`-based), not just a manual grep — re-verified passing as part of this phase's full test run.
- **Upload validation / rate limits / CORS / JWT expiry / RBAC / S3 privacy / error-response leakage**: all built and tested in Phases 1/3 (`tests/unit/test_config.py`'s production-guard matrix, `tests/unit/test_upload_validation.py`, `tests/integration/test_auth_rbac.py`'s RBAC/401/403 matrix and rate-limit/CORS/security-header checks, `services/ingestion/storage.py`'s `S3Storage` never generating a public URL) — re-verified passing, not re-built here.

## Frontend auth token storage: sessionStorage, not localStorage

**Decision:** `frontend/src/api/client.ts`'s `tokenStore` keeps the JWT (and
role) in `sessionStorage`.

**Trade-off, stated plainly:**
- **What we give up:** a user who closes the tab (not just reloads it) has to
  log in again. No "stay signed in across browser restarts."
- **What we gain:** an XSS payload that manages to run in one tab cannot
  smuggle a long-lived credential out to be replayed later from a different
  tab, a different session, or after the browser restarts — the token dies
  with the tab that was compromised. `localStorage` has no such boundary: a
  token written there is readable by any script in that origin for as long as
  the browser profile exists, including well after the user believes they've
  "left" the app.
- **Why this is the right call for an underwriter workbench** (as opposed to,
  say, a long-lived consumer app where session persistence matters more): the
  people using this tool are internal staff on shared or managed machines,
  reviewing sensitive applicant data. A short-lived, tab-scoped session is a
  small daily inconvenience traded for a meaningfully smaller blast radius if
  a dependency-supply-chain XSS (CLAUDE.md's other guardrails aside) ever gets
  a foothold in the frontend bundle.
- **What this does NOT protect against:** an XSS payload that runs *while the
  tab is open* can still read `sessionStorage` and use the token for the rest
  of that session — sessionStorage is not immune to XSS, only to token
  *persistence* beyond the tab's lifetime. The real XSS defenses are
  upstream of this decision: no `dangerouslySetInnerHTML` anywhere in the
  codebase, the adverse-action notice's structured JSON is rendered as text
  fields (not raw HTML) with every field passed through Jinja2's `tojson`
  filter server-side, and React's own default JSX escaping everywhere else.
- **What a production hardening pass would add:** an HttpOnly, Secure,
  SameSite=Strict session cookie issued by the backend instead of a
  client-readable token at all, which closes the "still exploitable while the
  tab is open" gap above. Noted here as the acknowledged next step, not
  implemented in this hackathon build (it would require a CSRF-token pattern
  alongside it, which is a bigger change than Phase 7's scope).
